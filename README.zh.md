# 电子相册（嵌入式 Linux / C / DRM 直显）

> **说明**：这是开发时的完整中文设计笔记（最详细的一份）。仓库的入口文档是
> [README.md](README.md)（英文）。
> 文中"目录结构"一节写的是开发目录，包含 `bmp/`（生成产物）和 `inc/ lib/`（厂商
> DRMwrap 库）；仓库里这三样都**不包含**：`bmp/` 用 `make assets` 重新生成，
> DRMwrap 从你自己的厂商 SDK 拷进 `inc/ lib/`。PC 端测试不需要它们。

RK1808 + aarch64-linux-gnu + DRM 直显 1024×600 + 电阻/电容触摸屏。

题目 5 条要求全部完成，两道附加题（**6 个小游戏** + **密码锁登录**）也全部完成。
**所有界面图片、按钮图、牌面、棋子、方块、蛇身都是代码生成的**，不依赖任何外部素材。

## 一、先看这 6 行（平台规格）

| 项目 | 值 | 依据 |
|---|---|---|
| 分辨率 | **1024 × 600**（已确认） | `share/showbmp.c` 里的硬编码边界 |
| 像素格式 | **XRGB8888**，内存序 `[B][G][R][X]` | `DRMwrap.c` 的 `drmModeAddFB(depth=24, bpp=32)` + `showbmp.c` 的写入顺序 |
| 图片格式 | **BMP**：24bit 全屏图 / 32bit 按钮图（带 alpha） | 板上没有 libpng/libjpeg，自己解 BMP 最省事 |
| 触摸设备 | **不用指定，程序自动识别**（见第四节） | 扫描 `/dev/input/event*`，按能力位打分 |
| 交叉编译 | `aarch64-linux-gnu-gcc` + `libdrm` + `libDRMwrap` | 根目录 `Makefile` |
| 显存行距 | 必须用 `drm.pitch`，**不要假设 = width×4** | `DRMcreateFB()` 的返回 |

> `*_bg.bmp`、`btn_*.bmp`、`photo_*.bmp`，剩下的游戏素材用到再说。

```bash
cd /root/album && chmod +x main
```


## 四、触摸设备是怎么自动找到的

`/dev/input/` 下通常有键盘、电源键、鼠标、触摸好几个 event 设备，编号跟接线和
驱动加载顺序有关。写死 `event2` 换一块板子很可能就是鼠标，程序看起来"完全没反应"。
所以 `touch.c` 扫描 `/dev/input/event0..31`，读每个设备的能力位再打分：

| 能力 | 权重 | 说明 |
|---|---|---|
| 有 `ABS_MT_POSITION_X` 和 `Y` | **+100** | 多点协议 → 现代电容屏 |
| 有 `ABS_X` 和 `ABS_Y` | **+70** | 单点协议 → 电阻屏 |
| 有 `BTN_TOUCH` | **+20** | 明确声明是触摸 |
| 有 `REL_X` 或 `REL_Y` | **一票否决** | 相对坐标 = 鼠标 |
| 一个绝对轴都没有 | **一票否决** | 键盘 / 电源键 |

最高分的那个就是触摸屏；**全是否决时会明确报错**并提示手动指定，
而不是随便挑一个（那样会出现"点了没反应"这种最难查的现象）。

> 为什么鼠标必须一票否决：有些鼠标驱动也会报 `BTN_TOUCH`，只按 `BTN_TOUCH`
> 判断会把鼠标当成触摸屏。用 `REL_X/REL_Y` 否决才可靠。

这段判定是**纯函数**（只吃能力位掩码，不碰真实设备），放在 `test/autodetect.c`
并用假掩码做了单测：单点屏、多点屏、鼠标、键盘、同时有绝对轴和相对轴的怪设备、
多候选挑优与顺序无关、全否决时返回失败。跑法见第六节。

## 五、操作说明

### 密码锁（附加题 2）

1. 开机进入密码界面，**初始密码 1234**，输满 4 位自动校验（也可按"确定"）。
2. 连续错 3 次 → 提示 `TOO MANY ERRORS, WAIT 3s` 并暂停 3 秒。
3. 主界面点 **"其他"** → 进入改密码界面，**新密码要连输两遍**，一致才生效。
4. 新密码写入 `account.cfg`，重启仍然有效。

> 密码不是明文存的，存的是"盐 + FNV-1a 32bit"的哈希，强度说明见第九节。

### 相册（题目 1–5）

| 题目要求 | 实现 |
|---|---|
| 1. 显示主界面 | 开机解锁后进主界面 |
| 2. 主界面 6 个入口 | 相册 / 游戏 / 多媒体 / 其他 / 退出 / 选项 |
| 3. 相册二级界面 | 手动 / 自动 / 退出 / 选项 |
| 4. 自动播放每 3 秒切换 | 点"自动"，默认 3000ms，底部有进度条，循环播放 |
| 5. 手动触摸上下翻页 / 退出 | 点"手动"：**上半屏 = 下一张，下半屏 = 上一张**，**右下角「退出」键 = 返回**（左上角也行） |

补充规则：

- **自动播放时碰一下屏幕 → 自动切到手动模式**（弹提示条），避免"点了照片却还在自动跑"。
- **任何界面左上角（x<200, y<100）都是返回**，不依赖按钮。
- **相册播放页（手动/自动）右下角还有一个常驻「退出」键**：图片底色是任意照片，左上角的文字提示未必看得清，所以给一个实体按钮，180x64、位置 (832,498)，和游戏页 chrome 按钮同一套样式。
- 照片是**翻到才解码、解码后缓存**，内存占用与照片总数无关。
- 没有 `photo_*.bmp` 时显示 `no_photo.bmp` 占位框，而不是白屏。

### 选项

点"选项"改自动播放间隔：**1 / 3 / 5 / 10 秒**，当前生效值显示在按钮下方。

## 六、PC 端测试（不用等板子）

`test/` 里把 DRM 换成一块普通内存、把触摸换成脚本点击，**整套逻辑在 Windows 上就能验证**。

```bat
cd test
mingw32-make -f Makefile check   :: 单测 + 整机冒烟，一条命令全绿
mingw32-make -f Makefile unit    :: 只跑两个单测(秒级)
mingw32-make -f Makefile run     :: 只跑整机状态机(会导出画面)
```

`clicks.txt` 是触摸脚本，每行 `x y 按下前等待毫秒`；`swipe x0 y0 x1 y1 等待` 是滑动；
`wait N` 是只等不点（用来等自动播放真的切一张）。

**测试桩的三个关键设计**（都是踩坑后加的）：

1. **等待要分片、且用绝对时刻判断**。主循环的自动播放计时在 `touch_poll()` 之外判断；
   如果桩在"等待 3400ms"时一觉睡到底，计时器永远没机会触发，
   "每 3 秒自动切图"这条**根本测不到**。现在等待切成小片还回主循环。
2. **别用"剩余时间累减"**：`nanosleep` 一旦提前返回（EINTR），剩余时间不归零，
   日志里会看到"开始等待 3400 ms"反复刷屏、PRESS 永远发不出来。
   现在记录**绝对截止时刻**，用 `CLOCK_MONOTONIC` 比大小。
3. **抽帧导出**：全流程几百帧，每帧 1.76MB 的 BMP 光写盘就几百兆。
   现在每 20 帧导出一张、缩到 1/2；要看细节设 `DRM_STUB_ALL=1` 恢复全帧全尺寸。

> 测试脚本最后一步点了"退出"，程序自己收拾干净结束；所以 `make check` 的退出码就是结论，
> 不需要外部超时杀进程（`SMOKE_NO_END_QUIT=1` 可关掉这个自动收尾，手动观察常驻行为）。

### 性能实测（PC 上量级参考，板上同量级）

| 操作 | 耗时 |
|---|---|
| `image_load_bmp` 解码一张 1024×600 24bit BMP | **2.4 ms** |
| `image_blit` 整屏贴图（1 像素 4 字节 memcpy） | **0.7 ms** |
| `image_blit_alpha` 整屏带 alpha 贴图 | **0.4 ms** |

按 3 秒切一张算，一帧绘制不到 4ms，余量极大。
真正要注意的是 `display_present()` → `drmModeSetCrtc()`，由 DRM 驱动决定，一般 5~16ms。

## 七、和 share 里原示例代码的 5 处必要改动

### 1. `ts.c` 的 `get_xy()` 是死等的，必须换掉

原版阻塞在 `read()` 里直到抬手 → **不碰屏幕程序就永远卡住，"每 3 秒自动切图"无法实现**。
`album/touch.c` 改成 `poll()` 带超时，并**把触摸拆成按下/抬起两个事件**：
主循环才能一边计时一边收触摸、按钮才有按下高亮、按住拖动才能变成滑动手势。

### 2. `showbmp()` 里 1024/600 硬编码

原版 `lcd_p[((y+j)*1024+(x+i))*4+0]`：屏幕尺寸写死、行距假设等于 `width*4`。
`image.c` 改成传 `pitch` 进来并自动裁剪越界区域；另外原版**只支持自下而上的 BMP**，
Photoshop 导出的"自上而下"（`h` 为负）会花屏，新代码两种都支持。

### 3. 显存只有一块，注意撕裂

现在是"单缓冲 + 直接改显存 + 每帧 SetCrtc"，切换时有轻微撕裂。做实验够用；
要顺滑就用 `DRMcreateFB()` 申请第二块显存做双缓冲，画完再切 `fb_id`。

### 4. 按钮从"烧在图里"改成独立小图

一开始按钮全画在 1024×600 背景大图里，后果是：加按钮要重出背景图、**做不出按下高亮**、
界面代码还得维护一份和图片重复的坐标表。现在背景只画标题光带和面板，
按钮是独立小图（`btn_*.bmp` + `btn_*_p.bmp`），`ui.c` 统一负责布局/绘制/命中。

### 5. 按钮图必须是 32bit 带 alpha，不能用 24bit

24bit BMP 没有 alpha 通道，加载器会把 A 填 0，带 alpha 贴图时**整块画不出来**
（现象：按钮全消失，只剩背景）。现在 `tools/ui_style.py` 的 `save_bmp32()`
手写 32bit BMP 头部（BGRA 内存序），按钮圆角外是 `A=0`，圆角才真正透明。

```bash
python tools/gen_font.py        # 8x16 ASCII 点阵字库(输出到 album/font8x16.c)
```

所有卡片样式集中在一个文件：**`tools/ui_style.py`**（`THEME_MAIN/ALBUM/LOCK/GAME` 四套配色，
`card()` 负责圆角/描边/左侧色条/中英文字号）。改这一处，所有界面跟着变，
不会出现"主界面和相册风格不一致"。

> **改布局后必须把新坐标同步到 `album/main.c` 的 `layout_init()` 和 `album/games.h` 的常量**，三处要一致。

换自己的照片：

```bat
python photos\convert.py D:\我的照片 ..\bmp
```

等比缩放 + 中心裁切到 1024×600，命名 `photo_01.bmp`…，并逐个校验 BMP 头部。
命名必须是 `photo_` 开头、`.bmp` 结尾，程序自动扫描、按名字排序，上限 128 张。

## 九、密码方案说明（别高估它的强度）

`account.c` 用的是 **FNV-1a 32bit + 固定盐**，存在 `account.cfg` 里：

```
version=1
pin_hash=1A2B3C4D
```

- **它挡住的**：别人直接打开配置文件看到明文密码；随手乱试。
- **它挡不住的**：有备而来的暴力破解。4 位数字只有 1 万种可能，
  32bit 无迭代哈希，用普通电脑几秒钟就能跑完。
- **失败锁定**做了，但只是内存里的计数器（错 3 次暂停 3 秒），重启就清零。

课程实验够用。要真做产品应该换 SHA-256 + 多次迭代 + 把失败次数落盘。

**调试过程中真正修掉的 6 个 bug**（都写进代码注释了）

1. **2048 合并逻辑写错**：`collapse_line()` 里合并后多写了一个 `i++`，
   导致 `[2,2,2,2]` 变成 `[4,2,2]`。单测直接抓出来了。
2. **悔棋判据写错**：用"得分是否为 0"判断有没有走过棋，但第一步完全可能不合并、不得分。
   改成显式的 `g_has_snapshot` 标志。
3. **按钮 id 前缀不匹配**：按钮 id 是 `main_exit`，分发代码却拿 `"exit"` 去比，
   `strcmp` 永远不等，于是**点退出没反应，主循环空转 120 万次**。
   现在统一用 `ID_IS(id, "main_exit")`。
4. **注释里的 `*/` 提前结束了注释块**：写 `ABS_*/REL_*/BTN_*` 时中间的 `*/` 把注释断掉，
   报一堆 `unknown type name 'REL_'`，长得像编码问题。
5. **24bit 图没有 alpha → 带 alpha 贴图整块不显示**：按钮全部"消失"。
   改为按钮专用 32bit BMP（见第七节第 5 点）。
6. **改密码界面返回没反应**：`go_back()` 的 `switch` 漏了 `SCREEN_PIN` 分支，
   人被困在密码键盘页。补上后正常回主界面。
